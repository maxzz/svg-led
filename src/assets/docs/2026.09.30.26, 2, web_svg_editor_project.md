I updated the plan: there's now a "Component rules" section, and the key-decisions bullet about avoiding effects is broadened to cover components.

**Instead of `useEffect` and `useCallback`:**
- **Event handlers** come from `useSetAtom(actionAtom)`. That setter never changes between renders, so there's nothing for `useCallback` to do.
- **Computed values** become derived atoms.
- **Subscriptions** use `atom.onMount`. This covers window listeners, `ResizeObserver` and Valtio `subscribe`. `onMount` runs while something is using the atom and returns its own cleanup.
- **Per-element or per-anchor state** uses `atomFamily` from `jotai-family`, which the project already has, keyed by node id.
- **DOM and editor objects** are handed to a setter atom through a ref callback, or through Monaco's `onMount` callback. This applies to the canvas `<svg>` and the Monaco instance.

**Where atoms live:**
- **Used by one component:** a separate file next to that component, named `9-atoms-<component>.ts`. This follows the template's existing `9-types-*.ts` files that sit next to the dialogs.
- **Shared:** atoms used by several components or controllers go in `src/store/4-editor/`.
- **Promotion:** when a local atom gets a second user, it moves to `store/`.

The plan includes an example layout for the toolbar and the Monaco host. The first todo now also says to apply these rules to all new components.

The `9-atoms-` prefix is my choice. If you'd rather use another name, such as reusing `9-types-`, tell me and I'll update the plan.

**What was added**
- **Commands** (`src/commands/`): one registry holds every action with its label, shortcut and enabled check. The main menu, the "more" menu, the command palette, the help dialog and the keyboard controller all read from it.
- **Controllers** (`store/5-controllers/`): a keyboard controller (the active tool gets keys first, then commands, then tool letters and arrow nudges), a clipboard controller (copy, cut and paste as SVG markup), and the code-sync controller.
- **UI**:
  - Top center: toolbar with the lock and a hint line.
  - Top left: hamburger menu laid out like your third screenshot.
  - Top right: viewBox and code-panel buttons.
  - Bottom: zoom, undo/redo and help.
  - Dialogs: command palette, find on canvas, and shortcuts help. The help dialog's modifier list comes from the same table the tools use.
- **Properties popup**: sections are registered by node kind and show "mixed" for multi-selection. With nothing selected it shows the drawing tool's style or the document's viewBox and size.
- **viewBox**: a "fit" dialog with linked or per-side padding, keep-aspect and center; its values are saved under their own key. A separate settings dialog has presets, add/remove viewBox, and setting width and height from the viewBox.
- **Code panel**: Monaco is lazy-loaded with local workers (no CDN). It slides out and can be resized. Two-way sync is debounced and guarded against loops. Parse errors show in a bar above the editor and as line markers. Selecting on the canvas highlights the lines; clicking a line selects the element.

**Changes outside the plan**
- **Selection survives code edits**: re-parsing the source used to give every node a new id, which dropped the selection on each keystroke. Nodes now keep their old ids by position when the element type matches (`reuseNodeIds`, with a test).
- **Rounded geometry**: moved or scaled shapes are rounded to the document precision, so the model matches the source text.
- **Template fix**: `CommandDialog` rendered its hidden title outside the dialog, so it appeared on the page even when closed.

**Checked in the browser**: menus, stroke edits, Ctrl+Z, fit-to-viewBox, code-to-canvas and canvas-to-code sync, parse errors, click-line-to-select, double-click into points mode, and dragging an anchor. Drags were simulated with pointer events, because the browser tools can't drag on the canvas or type into Monaco.
