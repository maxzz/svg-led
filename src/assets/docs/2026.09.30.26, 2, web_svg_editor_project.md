The primary purpose of this project is to edit SVG files—much like in Adobe Illustrator—but within a web application.
The user interface concept resembles that of the popular website excalidraw.com.
	
The application's entire workspace consists of a canvas where work with the SVG image takes place.


The first screenshot shows the application's workspace. The second screenshot shows the form when it is selected; a popup appears on the left displaying properties that can be modified for the selected form. It is possible to select multiple forms.

Two modes must be implemented: the first allows selecting SVG paths, while the second enables working on the points of a selected paths or on any of the shapes defined in the SVG format—such as rectangles, circles, and so on.

At the top of the canvas, there is a toolbar containing the working tools; in the left corner of the toolbar is the menu shown in the third screenshot.
	
The application must provide the ability to work with shape points defined in the same way as in Adobe Illustrator. You can check how Adobe Illustrator points mapped to SVG for example "Adobe Illustrator Anchor Point Types vs. SVG Commands".
Working with points is very convenient, as this feature is implemented in Adobe Illustrator.	
	
Unlike Adobe Illustrator, this application needs to support the ViewBox; specifically, the ViewBox should be displayed as an application option, and there must be functions to scale selected shapes to fit within the box, including an option to specify padding via a dialog.
	
As for the toolbar and tools options, they should be saved using Local Storage; options specific to an individual tool should be stored under a separate key to avoid cluttering the options object structure.	
	
Regarding the SVG source code: there should be a panel sliding out from the left containing the Monaco Editor. 
Above the editor, there needs to be a checkbox to enable synchronization between the SVG source code and the corresponding curves on the canvas—and vice versa; selecting an element on the canvas should highlight the corresponding line of code in the editor.	

Regarding canvas operations: if the current shape's edit mode is selected, it must be possible to drag all selected points, as well as delete and add new points along the path. This requires using Control, or Shift, or Alt key combinations which will modify the behavior of the selected tool.

When editing points on a shape, it is necessary to have additional lines for controlling the point, similar to how it is done in Adobe Illustrator.
	
For state management, the React components should use either Jotai or Valtio—
whichever is more appropriate—instead of standard state management provided by React.
This simplifies component reuse throughout the application.
Implement the new functionality in separate files/folders so that it does not mix with the rest of the code.

Minimize the use of `useCallback` and `useEffect` in React components in favor of Jotai’s `set` atoms and derived atoms (where necessary), or use Valtio’s reactivity where appropriate.

I updated the plan: there's now a "Component rules" section, and the key-decisions bullet about avoiding effects is broadened to cover components.

**Instead of `useEffect` and `useCallback`:**
- **Event handlers** come from `useSetAtom(actionAtom)`. That setter never changes between renders, so there's nothing for `useCallback` to do.
- **Computed values** become derived atoms.
- **Subscriptions** use `atom.onMount`. This covers window listeners, `ResizeObserver` and Valtio `subscribe`. `onMount` runs while something is using the atom and returns its own cleanup.
- **Per-element or per-anchor state** uses `atomFamily` from `jotai-family`, which the project already has, keyed by node id.
- **DOM and editor objects** are handed to a setter atom through a ref callback, or through Monaco's `onMount` callback. This applies to the canvas `<svg>` and the Monaco instance.

**Where atoms live:**
- **Used by one component:** a separate file next to that component, named `9-atoms-<component>.ts`. This follows the template's existing `9-types-*.ts` files that sit next to the dialogs.
- **Shared:** atoms used by several components or controllers go in `src/store/4-editor/`.
- **Promotion:** when a local atom gets a second user, it moves to `store/`.

The plan includes an example layout for the toolbar and the Monaco host. The first todo now also says to apply these rules to all new components.

The `9-atoms-` prefix is my choice. If you'd rather use another name, such as reusing `9-types-`, tell me and I'll update the plan.
