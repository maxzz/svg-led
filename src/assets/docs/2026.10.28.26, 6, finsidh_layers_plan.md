**How it works**
- **Reorder:** drag any row. If the row is selected, the whole selection moves and keeps its stacking order. Dropping on the top or bottom edge of a row places the layers above or below it, and dropping on the middle of a group row puts them inside the group, on top. Layers stay in the same place on the canvas when they move between groups with different transforms. A group can't be dropped into itself, and the isolated group only accepts drops inside it.
- **Rename:** double-click the name, or press the new **F2** command with one element selected. Enter applies, Escape cancels, and an empty name removes the `id`. Spaces become underscores, and a duplicate or invalid id is refused with a red field and a toast.
- **Eye/lock sweep:** press an eye or padlock and drag up or down. Every row you cross gets the state of the first row, and the whole sweep is one undo step.

**State and code layout**
- There's no `useState`, `useEffect` or `useCallback` in the new code. Gestures are write-only Jotai atoms, and per-row flags are derived atom families.
- Document edits go through the existing Valtio store and `commitHistory()`, so they can be undone.
- Motion animates the drop indicator, which glides between rows, and the drag ghost. The ghost follows the pointer through Motion values, so pointer moves don't re-render React.

**User**

When performing a drag-and-drop operation in the Layers panel, if the last item is an expanded group, it becomes impossible—or at least very difficult—to move an element to the very end of the tree, because it always ends up inside that last expanded group. 
To address this, the logic should account for the mouse position: if the item is being dragged toward the "children" of that last expanded group, it should indeed be added to that group (i.e., assigned to that parent). 
However, if the mouse is moved closer to the left edge, the item should instead be placed at the same hierarchical level as the expanded elements themselves.
